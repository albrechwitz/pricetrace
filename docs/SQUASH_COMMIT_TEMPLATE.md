# 기능 PR의 squash 커밋 기록

Git 담당이 아래 틀을 실제 squash 커밋의 제목과 본문에 채운다. `<...>`는 확정된 값으로 바꾸고, 원본 커밋 목록은 PR의 전체 목록을 기록한다. 해당 사항이 없으면 이유와 함께 `없음`으로 명시한다. PR URL만 남기는 방식은 이 템플릿을 충족하지 않는다.

```text
<type>(<scope>): <기능 변경 요약>

목적:
<해결한 문제와 변경 이유>

변경 동작:
<변경 전후의 사용자 동작 또는 기술적 결과>

원본:
- 브랜치: <원본 작업 브랜치>
- 대상 브랜치: stage
- Base SHA: <병합 직전 PR base의 40자리 전체 SHA>
- Head SHA: <검증된 PR head의 40자리 전체 SHA>
- PR: <원본 PR의 전체 URL>

원본 커밋 목록:
- <40자리 전체 SHA> <커밋 제목>
- <필요한 만큼 모든 원본 커밋을 나열>

변경 파일 범위:
<변경된 파일 경로와 각 파일 또는 묶음의 역할>

검증:
- 담당: <작성자와 독립된 검증 담당>
- 대상 SHA: <검증된 원본 head의 40자리 전체 SHA>
- 내용 대조: <검증된 diff·파일 해시와 최종 병합 후보의 일치 결과>
- 결과: <검사별 통과·실패·미실행 및 이유>

남은 한계:
<남은 제약과 후속 작업 또는 없음>
```

Git 담당은 병합 직전 원본 PR의 base/head, 전체 커밋 목록, 변경 파일과 검증 기록을 대조한다. 검증 후 내용이 바뀌면 영향받는 검증과 템플릿을 갱신한다. 빈 필드나 미완성 플레이스홀더가 있으면 squash하지 않는다.

이 본문은 원본 작업 브랜치를 삭제한 뒤에도 변경 내역과 검증 근거를 텍스트로 보존한다. 기록된 SHA의 원본 커밋 객체가 영구히 조회된다는 보장은 아니다. 원본 커밋 객체의 보존이 필요하면 커밋을 유지하는 merge를 사용한다.

`stage → main` 승격 PR에는 squash를 사용하지 않는다. 검증된 `stage`의 기능 커밋과 기록을 유지하는 merge로 승격한다.
